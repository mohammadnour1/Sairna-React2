    لوحة إدارة سيرنا — من Swagger لتطبيق شغّال على بيانات حقيقية

    هالدليل بيشرح لوحة الإدارة على /admin: كيف انعزلت عن موقع المسافرين، شو اكتشفنا عن الـ Dashboard API لما جرّبناه فعلياً، كيف بتمشي البيانات من الخادم للشاشة، وليش أخدنا كل قرار. اقراه بعد دليل الموقع، لأنو كتير أفكار هون مبنية عليه.

    01

    نظرة عامة

    لوحة الإدارة واجهة عربية (RTL) لحسابات المشرفين (ADMIN). منها بيدير المشرف شركات النقل والرحلات والحجوزات، وبيتابع المستخدمين والمدن. كلها بنفس مشروع React، بس معزولة تماماً عن موقع المسافرين.

    🎨 نفس الهوية

    نفس خط Cairo والألوان والـ tokens والأزرار والـ Modal والـ dark mode تبع الموقع. هي امتداد رسمي للموقع، مش قالب admin جاهز.

    🔌 بيانات حقيقية بس

    كل رقم وجدول جاي من الـ Dashboard API. الأرقام المحسوبة (متل المقاعد المحجوزة) محسوبة من responses حقيقية ومكتوب إنها محسوبة.

    🧱 معزولة

    client وتوكن وأحداث 401 ومفاتيح cache لحالها. انتهاء جلسة الأدمن ما بيطلّع المسافر من حسابه، والعكس كمان.

    كيف تفتحها

npm run dev

# افتح بالمتصفح
http://localhost:5173/admin      # بيحوّلك على /admin/login إذا ما في جلسة

    الـ Dashboard API — شو قال Swagger وشو طلع فعلياً

    Swagger بيوثّق شكل الطلبات (DTOs) بس. ما بيوثّق شكل الردود ولا أي query params. لهيك جرّبنا الـ API الحقيقي بحساب أدمن وسجّلنا كل شي بـ docs/api/ADMIN_API_NOTES.md.

    الـ endpoints الـ 18

    MethodPathBody (DTO)مين بيستعمله
    POST/auth/login{ email, password }صفحة الدخول
    GET/auth/me—الجلسة + الهيدر
    GET/overview—نظرة عامة
    GET/cities—المدن + فورم الرحلة
    GET/companies—الشركات + الفلاتر + فورم الرحلة
    POST/companies{ name*, logoUrl? }إضافة شركة
    PATCH/companies/{id}{ name?, logoUrl?, isActive? }تعديل/تفعيل

    GET/trips—الرحلات + التحليلات
    POST/tripsCreateTripDto (7 حقول مطلوبة)إضافة رحلة
    GET/trips/{id}—تفاصيل الرحلة
    PATCH/trips/{id}UpdateTripDto (+ status)تعديل الرحلة

    GET/bookings—الحجوزات + كل الأرقام المشتقة

    شكل الردود الحقيقي

    Endpointالردملاحظة مهمة
    /overview{ customers, companies, upcomingTrips, totalBookings, confirmedBookings }أرقام بس، ما فيه قوائم
    /tripsarray، كل رحلة مع company/origin/destinationما فيه _count ولا availableSeats
    /trips/{id}نفس الشي + _count.bookingSeats + availableSeatsالمقاعد بالتفاصيل بس

    /auth/login{ accessToken, tokenType, portal: "dashboard", user }نفس شكل الموقع

    ⚠️ مفاجآت غيّرت التصميم

    DELETE شركة = أرشفة

    الرد { message: "COMPANY_ARCHIVED" }، والشركة بتضل موجودة بـ isActive: false. لهيك الزر اسمه «أرشفة» مش «حذف»، والشركة المؤرشفة بيظهرلها زر «تفعيل».

    DELETE رحلة = إلغاء

    الرد هو الرحلة نفسها بـ status: "CANCELLED"، وبتضل بالقائمة. لهيك الزر اسمه «إلغاء الرحلة»، وبترجع «متاحة» من التعديل.

    الخادم ما بيتحقق من logoUrl

    قبل "not-a-url" بدون مشكلة، فالفحص صار بالفورم (validateCompany).

    أكواد أخطاء جديدة

    INVALID_COMPANY (رحلة لشركة موقوفة)، SAME_CITY، INVALID_TIMES. كلها مترجمة وبتظهر تحت الحقل المعني.

    درس مهم: الـ endpoint اسمه DELETE، بس سلوكه الحقيقي أرشفة. لو صدّقنا الاسم كان الزر رح يكذب عالمستخدم. جرّب، لا تفترض.

    قواعد التحقق من الخادم (من رد 400 حقيقي)

    companyId / originId / destinationId : integer ≥ 1
departureAt / arrivalAt              : ISO 8601 date string
price                                : integer ≥ 0
totalSeats                           : integer, 1 … 60
    05

    الجلسة والحماية

    1. الـ client

    كل طلب بياخد التوكن من sairna-admin-token. إذا رجع 401 من أي مكان غير صفحة الدخول، منمسح التوكن ومنبعت حدث.

    adminClient.interceptors.response.use(
  (response) => response,
  (error) => {
    const status = error.response?.status
    const hadToken = Boolean(error.config?.headers?.Authorization)
    if (status === 401 && hadToken && url !== adminEndpoints.login()) {
      clearAdminToken()
      adminAuthEvents.emitUnauthorized()   // مش authEvents تبع الموقع!
    }
    return Promise.reject(error)
  },
)

    2. AdminAuthContext — آلة حالات صغيرة

    statusمتىشو بيعرض AdminProtectedRoute
    guestما في توكنتحويل لـ /admin/login مع state.from
    loadingفي توكن و /auth/me لسا عم يحمّلSpinner «جارٍ التحقق من جلسة الإدارة...»
    authenticatedme رجع وrole = ADMINالـ layout والصفحة
    forbiddenme رجع بـ role تاني«لا يملك هذا الحساب صلاحية الإدارة» + خروج
    errorme فشل لسبب غير 401 (نت مثلاً)«تعذّر التحقق» + حاول مرة ثانية
    ليش الـ user مش محفوظ بالـ storage؟ لأنو مصدر الحقيقة دايماً GET /auth/me. التوكن بس هو اللي بينحفظ. هيك إذا تغيّر دور الحساب بالخادم، الواجهة بتعرف.

    3. تسجيل الدخول

    1. تحقق محلي: إيميل صحيح + كلمة مرور مش فاضية.
    2. POST /auth/login ← إذا ما في توكن، أو الـ role مش ADMIN ← خطأ واضح بالفورم.
    3. «تذكرني» مفعّلة ← localStorage، وإلا ← sessionStorage (بتنمسح لما تسكّر المتصفح).
    4. منحط الـ user بالـ cache فوراً (ما في طلب me زيادة)، ومنروح لـ from إذا كان تحت /admin، وإلا لـ /admin.
    حماية صغيرة: from بيتقبل بس إذا بلّش بـ /admin. هيك ما فيك تستعمل صفحة دخول الإدارة لتتحوّل لصفحة تانية من الموقع.

    4. الخروج

    ما في logout endpoint، فالخروج محلي: منمسح التوكن ومنعمل removeQueries({ queryKey: ['admin'] })، وبضربة وحدة بتنمسح كل بيانات الإدارة من الذاكرة.

    الـ Routing و route.lazy

  lazy: load(() => import('./AdminRoot')),
  children: [

        …
      ] },

}

    ليش route.lazy مش React.lazy؟

    الـ data router بيحمّل الـ chunk قبل ما يرسم الصفحة، فما بنحتاج Suspense بكل مكان. والـ hydrateFallbackElement بيعرض Spinner لما تفتح /admin مباشرة.

    العنوان والـ breadcrumb من handle

    AdminHeader بيقرأ useMatches() وبياخد آخر handle.title. منه بيطلع عنوان الصفحة، والـ breadcrumb («لوحة الإدارة › الرحلات › تفاصيل الرحلة»)، وعنوان التاب.

    07

    القوائم: بحث، فلترة، ترتيب، صفحات

    الـ API ما بيقبل ولا query param، يعني كل القائمة بتوصل بطلب واحد. لهيك البحث والفلترة والترتيب والتقسيم لصفحات كلهن بالمتصفح.

    useListParams — الحالة بالرابط

    const DEFAULTS = { q: '', status: 'all', sort: 'name', page: '1' }   // ثابت برا الـ component
const [params, update] = useListParams(DEFAULTS)

update({ status: 'active' })   // ?status=active   — وبيرجع لصفحة 1 تلقائياً
update({ page: 3 })             // ?page=3
update({ status: 'all' })      // القيمة الافتراضية بتنشال من الرابط
    • ليش بالرابط؟ لأنك بتعمل refresh أو بتبعت الرابط لحدا، وبيشوف نفس النتائج بالظبط.
    • replace: true: ما منعبّي الـ history بكل حرف بتكتبه.
    • أي تغيير غير الصفحة بيرجّعك لصفحة 1، لأنو ما في معنى تضل بصفحة 5 بعد ما تغيّر الفلتر.

    أدوات utils/list.js

    الدالةشو بتعمل
    matchesQuery(q, ...fields)بحث بيتجاهل التشكيل والهمزات (normalizeArabic): «اللاذقيه» بتلاقي «اللاذقية»
    paginate(list, page)10 بالصفحة، وإذا الصفحة صارت برا النطاق (بعد فلترة) بترجع لآخر صفحة صالحة
    sortCopy + byTimeAsc/Desc، byText، byNumberDescترتيب على نسخة، ما منغيّر الـ cache أبداً
    countBy(list, getKey)عدّ سريع، متل عدد الرحلات لكل شركة
    البحث ما بيبعت طلب: SearchInput بيستنّى 250ms بعد آخر حرف، وبعدين بيكتب بالرابط. ولأنو الفلترة محلية، النتيجة فورية.

    فلاتر جاية من صفحات تانية

    من صفحة المستخدم «حجوزاته» ← /admin/bookings?user=42، ومن الشركة «عرض رحلاتها» ← /admin/trips?company=1. الفلتر الجاي من برّا بيظهر كـ FilterChip فيك تشيله.

    خيارات فلتر الحالة مبنية من الحالات الموجودة فعلياً بالبيانات (new Set(data.map(x => x.status)))، مش من لائحة مفترضة.
    08

    الصفحات واحدة واحدة

    📊 نظرة عامة /admin

    • البطاقات: كل رقم موجود برد /overview. الـ mapper ما بيفترض أسماء، بيمشي عالرد وبياخد كل قيمة رقمية (الفصل 10).
    • تحليلات الحجوزات لآخر 7 / 30 / 90 يوم: الحجوزات يومياً (أو أسبوعياً لـ 90)، حالة الحجوزات، أكثر الخطوط حجزاً، الحجوزات حسب الشركة.
    • أحدث الحجوزات والرحلات القادمة (المتاحة اللي لسا ما انطلقت، الأقرب أول).
    • زر تحديث بيعمل invalidate لكل ['admin'].

    🏢 شركات النقل

    • جدول: الشعار (أو الحرف الأول بلون الشركة)، الاسم، tag «تجريبية»، الحالة، عدد الرحلات.
    • بحث بالاسم أو الرقم، فلتر فعّالة/موقوفة، ترتيب بالاسم أو الأكثر رحلات أو الأحدث.
    • إجراءات كل سطر: عرض رحلاتها، تعديل، أرشفة (للفعّالة) أو تفعيل (للموقوفة).
    • الفورم بـ Drawer جانبي، مع معاينة للشعار متل ما رح يظهر بالجداول.

    🚌 الرحلات + تفاصيل الرحلة

    • الافتراضي: الرحلات القادمة مرتّبة من الأقرب. فلاتر: الموعد (قادمة/سابقة/الكل)، الشركة، الحالة، الترتيب.
    • الحالة بتعرض «انطلقت» للرحلة المتاحة اللي وقتها مضى (tripDisplayStatus).
    • عمود المقاعد المحجوزة محسوب من الحجوزات المؤكدة، لأنو القائمة ما فيها هالرقم.
    • صفحة التفاصيل: معلومات (بتوقيت دمشق)، إيرادات الحجوزات المؤكدة، خريطة إشغال المقاعد (2 + ممر + 2 متل الموقع)، وجدول حجوزات الرحلة مع إمكانية الإلغاء.

    🎫 الحجوزات + تفاصيل الحجز

    • البحث بيشمل: رقم الحجز، اسم وإيميل صاحب الحساب، المدن، وأسماء وأرقام المسافرين.
    • فوق الجدول: مجموع الحجوزات المؤكدة بالنتائج الحالية.
    • التفاصيل: المسافرين ومقاعدهم (الرقم بيفتح الاتصال tel:)، المبلغ، صاحب الحجز، الرحلة.
    • الإلغاء دايماً عبر ConfirmDialog. الزر بيكون معطّل للحجز الملغى أصلاً.

    👥 المستخدمون + تفاصيل المستخدم

    للعرض فقط (الـ API ما فيه تعديل). عدد الحجوزات محسوب من /bookings. التفاصيل: 4 بطاقات (كل الحجوزات، المؤكدة، الملغاة، قيمة المؤكدة) + جدول حجوزاته.

    📍 المدن

    للعرض فقط: الاسم، الإحداثيات، وعدد رحلات الانطلاق والوصول (محسوبين من /trips). زر «الرحلات منها» بيفتح الرحلات مفلترة باسم المدينة.

    🔐 دخول المشرف

    شاشة مقسومة: لوحة داكنة بهوية سيرنا (الشعار + «كل تشغيل سيرنا بمكان واحد») والفورم. على الموبايل اللوحة بتصير فوق.

    الفورمات وتوقيت دمشق

    المشكلة

    الخادم بيخزّن الأوقات UTC، و<input type="datetime-local"> ما إله منطقة زمنية، والمشرف بيفكّر بتوقيت دمشق. ولو المتصفح مضبوط على منطقة تانية (لابتوب مسافر مثلاً)، الحل الساذج new Date(value).toISOString() بيعطي ساعة غلط.

    الحل: utils/datetime.js

    // '2026-11-05T10:30' (مكتوب بتوقيت دمشق) → '2026-11-05T07:30:00.000Z'
export function damascusInputToISO(value) {
  const wallAsUtc = Date.UTC(y, mo - 1, d, h, mi)        // نعامل الأرقام كأنها UTC
  let ms = wallAsUtc - offsetMinutes(wallAsUtc) * 60000  // نطرح فرق دمشق
  ms = wallAsUtc - offsetMinutes(ms) * 60000              // تمريرة تانية لو تغيّر الفرق
  return new Date(ms).toISOString()
}

    offsetMinutes بيحسب فرق دمشق عن UTC بلحظة معيّنة باستعمال Intl.DateTimeFormat بـ timeZone: 'Asia/Damascus'. يعني ما في رقم «+3» مكتوب بالكود، وإذا تغيّرت قواعد التوقيت، المتصفح بيعرف.

    تحققنا: 10:30 دمشق ← 07:30Z، وهو نفس مثال Swagger بالظبط. والتحويل العكسي (isoToDamascusInput) رجّع نفس القيمة بـ 3 تواريخ مختلفة.

    فورم الرحلة

    • الشركة: الموقوفة بتظهر بس معطّلة (الخادم بيرفضها بـ INVALID_COMPANY)، إلا إذا كانت شركة الرحلة اللي عم تعدّلها.
    • الانطلاق لازم يكون بالمستقبل (للرحلة الجديدة بس)، والوصول بعد الانطلاق. ومدة الرحلة بتنحسب وبتظهر تحت الحقلين وانت عم تكتب.
    • السعر رقم صحيح أكبر من صفر. الخادم بيقبل 0، بس رحلة مجانية غالباً غلطة إدخال.
    • المقاعد من 1 لـ 60 (حد الخادم)، وبالتعديل ما فيك تنزل تحت عدد المقاعد المحجوزة.
    • الحالة (تعديل بس): متاحة / ملغاة.

    حدود معروفة وتمارين

    حدود من الـ API

    • ما في search/filter/pagination بالخادم، فكل قائمة بتنزل كاملة. هلق الأعداد صغيرة (117 رحلة، 60 مستخدم)، بس بآلاف السجلات لازم الخادم يدعم ?page=&q=.
    • ما في حذف نهائي للشركات والرحلات، ولا تعديل للمستخدمين أو المدن، ولا إنشاء حجز من الإدارة، ولا إشعارات.
    • ما في طريقة موثّقة لحذف شعار شركة بعد ما ينضاف.
    • ما في توثيق إذا إلغاء رحلة بيلغي حجوزاتها تلقائياً.

    تمارين للتعلّم

    1. ضيف عمود «تاريخ الإضافة» لجدول المستخدمين يقبل الترتيب بالضغط عالعنوان (فكّر وين لازم ينحط الـ sort: بالرابط).
    2. ضيف فلتر «من تاريخ / لتاريخ» لصفحة الحجوزات بالاعتماد على damascusDay.
    3. ضيف زر «تصدير CSV» للنتائج المفلترة (بدون مكتبة: Blob + URL.createObjectURL).
    4. بصفحة الرحلة، اعرض اسم المسافر لما تمرّق الماوس فوق مقعد محجوز. البيانات موجودة أصلاً بـ seatMap.
    5. اكتب لنفسك: ليش DEFAULTS لازم يكون برا الـ component؟ (تلميح: identity بالـ useMemo).
